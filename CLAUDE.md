# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

Velnora, a premium AI-powered web development agency site. The agency builds high-performance websites, SEO solutions, AI-powered digital solutions, and business automation for growing businesses. This repo is the agency's own marketing site.

**Phase 2 (frontend + backend/database/API) is done. The AI Client Handling Agent, the AI Lead Finder Agent, and the Admin Dashboard are now all built** (originally scoped as "Phase 4", "Phase 5", and "Phase 6" below, all three built ahead of Phase 3 at explicit request — the numbering in "Future phases" below still reflects the original plan). **The Admin Dashboard now has real email+password authentication** (`AdminUser`/`AdminSession`, httpOnly session cookies) instead of the original shared-token gate — see "Admin Dashboard" below. `/api/leads/*` still also accepts the legacy shared token for backward compatibility. Still no general multi-user auth (that's still Phase 3's `User` model), payments, or CRM. The architecture is deliberately structured so those can be layered on later without a redesign, see "Future phases" below.

## Stack (decided, do not re-litigate without reason)

- **React 19 + TypeScript + Vite**, not Next.js, chosen explicitly for this project over the platform's usual Next.js default.
- **Tailwind CSS v4** via `@tailwindcss/vite`. Theme tokens live in `src/index.css` under `@theme`.
- **Motion** (`motion/react`, the Framer Motion successor) for animation, plus a couple of scroll-reveal/whileInView patterns. No GSAP.
- **React Three Fiber + drei** for the hero's 3D visual only, lazy-loaded and gated behind `src/hooks/useCanRender3D.ts` (WebGL support + rough low-power heuristic) with a CSS/DOM fallback (`SceneFallback.tsx`) for everything else, including `prefers-reduced-motion`.
- **React Router**, one route today (`/`), kept so additional pages (e.g. a dedicated `/seo` page) can be added without restructuring.
- **react-helmet-async** for per-page SEO metadata. Add new pages' metadata to `src/lib/seoConfig.ts`, not inline in components.
- **Lucide React** for icons (single icon family, do not mix in another).
- **oxlint** for linting (`npm run lint`), not eslint.

**Backend** (`backend/`, a separate Node project, see `backend/README.md`): Express 4 + TypeScript + Prisma/PostgreSQL + Zod. Controllers thin, business logic in `services/`, every public POST body validated by a Zod schema in `validators/` before a controller sees it. Don't import backend code into the frontend or vice versa, they're separately deployable; shared concepts (e.g. the allowed `projectType`/`budgetRange` values) are intentionally duplicated in both places rather than cross-imported, keep both in sync by hand if you change one (frontend: `src/sections/Contact.tsx`'s `<select>` options; backend: `backend/src/validators/shared.ts`).

**AI Client Handling Agent** (`backend/src/ai/`, see backend/README.md's "AI Client Handling Agent" section): a chat consultant surfaced via `src/components/chat/FloatingChatWidget.tsx`, talking to `POST /api/ai/chat`. Provider-agnostic by design — business logic (`backend/src/services/aiChat.service.ts`) only imports from `backend/src/ai/providers/types.ts`, never the Anthropic SDK directly (that's isolated to `AnthropicProvider.ts`). To change what the agent knows, edit `backend/src/ai/knowledge/velnoraKnowledge.ts`; to change its tone/rules, edit `backend/src/ai/prompts/systemPrompt.ts`. Its only tool (`save_lead`) can create exactly one new `QualifiedLead` row and nothing else — no update, delete, or read access — that's the actual defense against prompt-injected destructive requests, not just prompt wording.

**AI Lead Finder Agent** (`backend/src/leadFinder/`, see backend/README.md's "AI Lead Finder Agent" section): researches businesses via Google Places, deterministically detects opportunities and scores them (never an AI judgment call, always traceable to observed facts), and drafts a personalized outreach email — reusing the Client Handling Agent's `AnthropicProvider`, not a second AI integration — into Gmail via OAuth. It never sends: `backend/src/leadFinder/gmail/GmailProvider.ts` has no send method of any kind. Every `/api/leads/*` route requires either a valid Admin Dashboard login session or the legacy `X-Admin-Token` header (`requireAdminAccess.ts`, checked in that order) — see "Admin Dashboard" below for the session mechanism. Reachable at `/internal/lead-finder` (lazy-loaded, not linked publicly, `noindex`) — a minimal testing interface, still gated by the shared token/`AdminTokenGate.tsx`/`useAdminToken.ts`, superseded for day-to-day use by the Admin Dashboard below, but kept as-is rather than removed.

**Admin Dashboard** (`src/pages/internal/admin/`, `backend/src/routes/admin.routes.ts`, see backend/README.md's "Admin Dashboard" section): the internal, protected home for triaging both AI agents' leads — real-time overview stats (`GET /api/admin/overview`, Prisma `groupBy` aggregates, never fabricated), `QualifiedLead` management (`/api/admin/client-leads/*`, including an IDOR-safe conversation-detail lookup that 404s before ever querying `AIConversation`), and the Lead Finder's leads (reuses and extends the existing `/api/leads` endpoint rather than duplicating it — new `search`/`priority`/`opportunityTypes`/`hasEmail`/`hasWebsite`/`sort` query params are additive and backward compatible, the old hardcoded sort order is still the default). No schema changes were needed to build any of this: it's a read/aggregate layer plus one status-update endpoint over the existing `QualifiedLead`/`AIConversation`/`Lead` models. Email generation and Gmail draft creation are exposed here too, but strictly reuse the Lead Finder's existing `generateEmailForLead`/`createDraftForLead` service functions — there is still no send capability anywhere in the codebase, the workflow is always generate → review → create Gmail draft → stop.

**Admin Dashboard authentication** (`backend/src/services/adminAuth.service.ts`, `backend/src/middleware/requireAdminSession.ts`, `src/pages/AdminLogin.tsx`, `src/lib/useAdminSession.ts`): a real, dedicated login system replacing the dashboard's original shared-token gate (`AdminTokenGate.tsx` is no longer used here, only by the standalone `/internal/lead-finder` page above). `AdminUser` (bcrypt `passwordHash`, never plaintext) and `AdminSession` (a SHA-256 hash of the session token, never the raw token, keyed to a random 32-byte cookie value) are new Prisma models — deliberately separate from the `User` model, which stays untouched schema-prep for a future general multi-role auth system. Login is `POST /api/auth/admin/login` (rate-limited, generic "Invalid email or password" for both a wrong password and a nonexistent email, constant-time-ish via a real bcrypt compare against a dummy hash either way); it sets an `httpOnly`, `SameSite=Lax` cookie (`velnora_admin_session`) — never readable from frontend JS. This only stays correct because the frontend never calls the backend cross-origin: the root `vercel.json` rewrites `/api/*` to the deployed Render backend, and `vite.config.ts`'s dev-server proxy does the same locally, so every request looks same-site to the browser regardless of where the backend actually runs. This went through two broken iterations first, both live: plain `SameSite=Lax` while the frontend called Render's `*.onrender.com` origin directly (genuinely cross-site, since Vercel and Render are different registrable domains) meant the browser silently refused to attach the cookie to the very next request checking the session, bouncing the admin straight back to the login page with no error shown; switching to `SameSite=None` fixed that but then hit third-party-cookie blocking (a separate browser privacy feature — Chrome's "Block third-party cookies," Safari's ITP — that rejects a cross-site cookie regardless of `SameSite`). Routing everything through one origin via the proxy fixed the root cause instead of chasing further cookie-attribute exceptions to it. See SECURITY.md's "Admin Dashboard security" section for the full history. `GET /api/auth/admin/me` and `POST /api/auth/admin/logout` round out the flow. The very first `AdminUser` is created once at server startup from `ADMIN_EMAIL`/`ADMIN_PASSWORD` env vars (`bootstrapInitialAdminUser` in `adminAuth.service.ts`) if no account with that email exists yet — the plaintext password is hashed immediately and never stored/logged/returned. `/api/admin/*` requires this session exclusively (`requireAdminSession()`); `/api/leads/*` accepts this session OR the legacy token (`requireAdminAccess()`), so the old `/internal/lead-finder` page and any existing token-based script keep working unchanged. Frontend: `AdminShell.tsx` checks the session via `useAdminSession()` and redirects to `/admin/login` (not under `/internal/`, see `robots.txt`'s own `Disallow: /admin`) when it's missing — this is a UX convenience, the backend independently re-verifies every request regardless of what the frontend does.

## Design system

- Single accent color: emerald (`--color-accent` family), deliberately chosen over the generic "AI purple" look. Do not introduce a second accent color.
- Neutral base is off-black (`--color-canvas` `#09090b`), never pure `#000`.
- Font: Geist Sans + Geist Mono (self-hosted via `@fontsource/geist-sans` and `@fontsource/geist-mono`), not Inter.
- Radius lock: `--radius-panel` (cards/panels) and `--radius-field` (inputs) plus `rounded-full` for buttons/pills. Don't introduce other radius values ad hoc.
- **Naming gotcha:** Tailwind v4 auto-generates color utilities from any `--color-*` key in `@theme`. Never name a theme color token the same as a built-in Tailwind scale key (this project hit exactly this bug: `--color-base` silently redefined the `text-base` font-size utility into a color utility, blacking out text). Check new token names against Tailwind's default font-size/spacing/radius scale before adding them.

## Conventions

- One component per file under `src/sections/` per landing-page section; `src/pages/Home.tsx` just assembles them in order.
- Reusable primitives live in `src/components/ui/`; layout chrome (Navbar/MobileMenu/Footer) in `src/components/layout/`; the 3D scene and its fallback in `src/components/three/`.
- Copy/content data (services, process steps, projects, nav items, tech stack) lives in `src/data/*.ts`, not inline in JSX, so it's easy to edit without touching layout code.
- No fabricated client logos, fake testimonials, or invented statistics. The portfolio section uses clearly-labeled concept projects; the tech-stack strip under the hero shows real technologies this site is actually built on (via Simple Icons), not client logos.
- Prefer real, provisioned integrations (via the Vercel Marketplace) over mocked services once a backend is introduced, check the `vercel:marketplace` skill before wiring one up.

## Future phases (do not build yet, but keep the door open)

- **Phase 4, client-handling AI agent: done** (see "AI Client Handling Agent" above), built ahead of Phase 3 at explicit request. Kept for history: it originally read "chat, lead qualification, extend the Contact form's `apiPost` call rather than rewriting it" — the agent is a separate `POST /api/ai/chat` endpoint instead, since it needed its own conversation/tool-call round trips that don't fit the single-shot `POST /api/project-inquiry` shape; the Contact form itself is untouched.
- **Phase 5, lead-finder agent: done** (see "AI Lead Finder Agent" above), also built ahead of Phase 3. The `Lead` Prisma model, previously pure preparation, is now the Lead Finder's actual data store — extended (not replaced) with `category`/`domain`/`opportunityTypes`/`analysis`/`evidence`/`emailSubject`/`emailBody`/`gmailDraftId` and a longer `LeadStatus` enum. Still distinct from `QualifiedLead` (the Client Handling Agent's own model, unprompted-discovery vs. mid-conversation-capture are different lifecycles).
- **Phase 6, admin dashboard: done** (see "Admin Dashboard" above), also built ahead of Phase 3. Kept for history: it originally read "to triage `ContactSubmission`/`ProjectInquiry`/`Lead`/`QualifiedLead` rows" — built as scoped, minus `ContactSubmission`/`ProjectInquiry` management (those remained out of scope for this pass; the dashboard covers `QualifiedLead` and `Lead` only, per the request that defined it). No Prisma schema changes were needed, the existing `analysis`/`evidence` JSON structure and status enums were already shaped for exactly this.
- Phase 3: general multi-user authentication (the `User` Prisma model already exists as preparation, no endpoint uses it yet), for a future multi-role system beyond the single Admin Dashboard account type. The Admin Dashboard itself now has real email+password login (`AdminUser`/`AdminSession`, see "Admin Dashboard authentication" above) — that gap is closed for the one internal tool that needed it, but there's still no per-operator audit trail (every admin session looks the same, there's no distinct "role" concept, and `/api/leads/*` still also accepts the legacy shared token for backward compatibility). A real Phase 3 should still add: multi-user roles/permissions, per-operator audit logging for admin actions, and a plan to eventually retire the legacy `LEAD_FINDER_ADMIN_TOKEN` path once nothing depends on it.
- Phase 7: deployment, monitoring, final security audit.
